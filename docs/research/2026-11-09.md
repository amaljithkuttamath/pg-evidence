# November 9: pgrx migration and joined-search controls

**Keep pgrx 0.19.3 for the preview. Qualify pg_search 0.26.6 for the external
comparison.** Neither decision changes the current build or the frozen benchmark.
This follows the [November 2 review](2026-11-02/README.md).

## What a pgrx upgrade would require

The [0.20.0-beta.0 release](https://github.com/pgcentralfoundation/pgrx/releases/tag/v0.20.0-beta.0)
appeared November 9; the latest non-prerelease was still
[0.19.3](https://github.com/pgcentralfoundation/pgrx/releases/tag/v0.19.3).
The beta needs Rust 1.99.1 and matching clang/libclang majors. Our
[validated build](../../packaging/versions.json) pins Rust 1.99.0. The
[tagged migration guide](https://github.com/pgcentralfoundation/pgrx/blob/v0.20.0-beta.0/v0.20.0-MIGRATION.md)
also replaces the interrupt macro with a function.

On [product main f3a2ce8](https://github.com/amaljithkuttamath/pg-evidence/tree/f3a2ce82ce93f901458d7ac10fe4a582a82fcc2f),
`git grep -n 'pgrx::check_for_interrupts!' -- src` finds four direct uses:
`src/ops.rs:219,474,782` and `src/retrieve.rs:51`. A version bump alone would
therefore leave incompatible source and toolchain pins. A future isolated
migration should update those calls, review the custom JSON datum conversion in
`src/db.rs`, and exercise cancellation, encoding errors and exact response bytes
against PostgreSQL. This was a source audit, not a beta build or a finding that
the current release mishandles those cases.

## What to compare in ParadeDB

- **Permissions:** [0.26.5, November 4](https://github.com/paradedb/paradedb/releases/tag/v0.26.5)
  shipped the [standalone index-read permission fix](https://github.com/paradedb/paradedb/pull/7023)
  via [#7114](https://github.com/paradedb/paradedb/pull/7114). A standalone
  whole-index aggregate can be denied when row-level security is in effect;
  an ordinary SQL scan can return the permitted subset. Use the latter for
  reader-visible counts. Never substitute a monitoring role's whole-index
  statistics for the restricted reader's result.
- **Plan and result identity:** [0.26.6, November 8](https://github.com/paradedb/paradedb/releases/tag/v0.26.6)
  supports [distance-ordered inner and semi equijoins](https://github.com/paradedb/paradedb/pull/7137)
  and [rank joins with certain pushed filters](https://github.com/paradedb/paradedb/pull/7298).
  These are distinct changes: the latter covers disjunctive text search, not
  arbitrary RLS predicates in a vector scan. For a top-k evidence query use an
  exact SQL reference with the same join multiplicity. For example, if a span
  has two matching tags, a semi join returns it once; a plain inner join can
  count it twice toward k. Compare allowed evidence IDs and resolved bytes,
  and save the actual plan before interpreting timing.

The paper [Fast Approximate Vector Joins via Offline-Online Co-Design, v2,
July 23](https://arxiv.org/abs/2603.16360v2) studies a different operation:
finding vector pairs within a distance threshold. Its results do not measure
top-k evidence retrieval after relational eligibility checks. Do not import
its timings as a baseline. Neither the upstream fixes nor the paper were
reproduced in this pass.

## Experiment decision

The [PostgreSQL 18 series](https://www.postgresql.org/support/versioning/),
[pgvector tag](https://github.com/pgvector/pgvector/blob/v0.8.7/CHANGELOG.md) and
[pgvectorscale release](https://github.com/timescale/pgvectorscale/releases/tag/0.9.1)
remain at 18.6, 0.8.7 and 0.9.1 respectively in the November 9 check.
Product main is unchanged. The [SQL control](../../baseline/README.md) still
uses a fixed envelope allowance, and no frozen eligible-set vector truth was
added. The local Docker daemon was unreachable during an image-inspection
preflight; no database correctness or performance run started. **Zero
optimization candidates and zero holdouts**; no change to the evaluator.
